# 13 迁移部署与上线运维

## 1. 目标

将现有 SQLite + `backend/data/results` 平滑迁移到 Neon PostgreSQL + Cloudflare R2，并在宝塔 Nginx 后运行 Web、Worker、Scheduler 和轻量 Redis。应用镜像由 GitHub Actions 构建，生产服务器只拉取镜像，不在服务器安装 Python/Node 依赖或执行镜像构建。迁移期间保护现有历史任务和版本链，具备回滚能力。

## 2. 生产拓扑

```text
Internet
  -> 宝塔 Nginx :443
      -> 127.0.0.1:18080

服务器 A：
- 现有 Java 服务
- 现有宝塔 Nginx
- web（只绑定 `127.0.0.1:18080`）
- worker（单并发）
- scheduler（只能有一个主实例）
- redis（仅 Docker 网络）

外部：
- Neon PostgreSQL（Direct connection + TLS）
- Cloudflare R2 HTTPS
- Sub2API HTTPS
- 邮件服务 HTTPS/SMTP

服务器 B：
- 仅保留现有 MySQL，不部署本项目组件
```

只有 Nginx 暴露 `80/443`。Redis 不绑定宿主机端口，FastAPI 只绑定回环地址。Neon 和 R2 均使用 TLS 出站访问。

低流量首发资源上限：Web 512 MB、Worker 1280 MB、Scheduler 192 MB、Redis 192 MB，`WORKER_MAX_JOBS=1`。服务器保留 4 GB Swap 作为突发保护，但 Swap 不能替代内存监控。

## 3. 权限与运维责任

| 操作 | 要求 |
|---|---|
| 部署镜像、数据库迁移 | 服务器运维权限 + 变更记录 |
| 业务密钥和 R2 配置 | 后台 `config.manage` |
| 数据迁移与对账 | `system.maintenance.execute` |
| 查看健康与日志 | `system.diagnostics.read` |
| 回滚配置 | `config.manage` + 审计原因 |

首个超级管理员由 CLI 创建；后续角色、会员、积分和业务密钥从后台操作。

## 4. 数据库结构与迁移记录

除各模块业务表外，迁移增加：

```text
data_migration_runs
- id uuid PK
- migration_type varchar             # sqlite_to_postgres/local_to_r2
- source_fingerprint varchar
- status varchar
- checkpoint jsonb
- total_count int
- success_count int
- failure_count int
- started_by uuid NULL
- started_at timestamptz
- completed_at timestamptz NULL
- report_object_key varchar NULL

data_migration_items
- id uuid PK
- run_id uuid FK data_migration_runs
- source_id varchar
- target_id uuid NULL
- source_path varchar NULL
- source_sha256 char(64) NULL
- target_object_key varchar NULL
- status varchar
- error_redacted varchar NULL
- updated_at timestamptz
- UNIQUE(run_id, source_id)
```

迁移工具必须可断点续跑，同一源记录重复执行不能创建重复资产。

## 5. 接口与命令设计

迁移优先采用服务器 CLI，避免通过公网 HTTP 传输本地历史文件：

```bash
python -m app.cli create-admin
python -m app.cli migrate-sqlite --dry-run
python -m app.cli migrate-sqlite --execute
python -m app.cli migrate-assets-to-r2 --dry-run
python -m app.cli migrate-assets-to-r2 --execute --resume RUN_ID
python -m app.cli reconcile-points
python -m app.cli reconcile-storage
```

后台只负责启动/查看维护任务，不接受任意文件路径：

```text
GET  /api/v1/admin/migrations
GET  /api/v1/admin/migrations/{run_id}
POST /api/v1/admin/migrations/{type}/dry-run
POST /api/v1/admin/migrations/{run_id}/execute
POST /api/v1/admin/migrations/{run_id}/resume
GET  /api/v1/admin/backups/status
POST /api/v1/admin/backups/verify
```

## 6. 迁移顺序

1. 冻结需求与表结构，备份当前代码、SQLite 和 `backend/data`。
2. 创建 Neon 生产分支、部署本机轻量 Redis、创建 R2 私有桶，执行空库迁移。
3. 创建首个超级管理员，后台配置并测试 Sub2API、R2、邮件。
4. 把旧系统置为只读，记录迁移起始时间和文件清单哈希。
5. 迁移 SQLite 用户归属：现有单用户资产默认归属首个管理员或指定迁移账号。
6. 上传本地图片到 R2，校验大小与 SHA-256，再写资产对象键。
7. 校验版本链、任务、资产数量和随机下载样本。
8. 在新系统执行上传、付费任务、失败退款、下载全链路。
9. Nginx 切换到新服务，先限量开放管理员和内部用户。
10. 观察 24-72 小时后解除灰度，旧数据至少保留 14 天再归档。

## 7. 配置与部署

启动层仅保留：

```text
DATABASE_URL
REDIS_URL
APP_CONFIG_MASTER_KEY
APP_ENV=production
PUBLIC_APP_URL
AUTH_TOKEN_PEPPER
AUTH_HASH_SALT
```

Sub2API、R2、邮件和业务限制在管理员后台配置。宝塔中的启动配置文件权限设为 `600`，不放在网站可下载目录。配置根密钥需要离线备份；丢失后数据库中的业务密钥将无法解密。

生产服务器使用 `docker-compose.server.yml`。该文件不包含 PostgreSQL、MinIO 和 Nginx，也没有本地构建指令：

```bash
docker compose -f docker-compose.server.yml pull
docker compose -f docker-compose.server.yml up -d
docker compose -f docker-compose.server.yml ps
```

`migrate` 容器在其他应用进程启动前执行 Alembic。首次上线后通过正在运行的 Web 容器交互式创建管理员：

```bash
docker compose -f docker-compose.server.yml exec web python -m app.cli create-admin
```

若首个管理员因初始密码输入错误或连续失败而锁定，只能在服务器容器内交互式恢复；密码不接受命令行参数，成功后清除该账户失败记录并撤销旧会话：

```bash
docker compose -f docker-compose.server.yml exec web python -m app.cli reset-admin-password
```

若首个管理员邮箱输入有误，通过另一个服务器交互命令修正。该命令要求重复确认新邮箱，清除新旧邮箱的失败记录、撤销旧会话并记录审计事件：

```bash
docker compose -f docker-compose.server.yml exec web python -m app.cli change-admin-email
```

GitHub Actions 仅在 `main` 分支质量门禁成功后发布 `linux/amd64` 应用镜像到 GHCR，并同时保留 `latest` 和提交 SHA 标签。流水线还把官方 `redis:7-alpine` 转存为同一公开包中的 `redis-7-alpine` 标签，使国内生产服务器无需访问 Docker Hub。首次发布后需要将 GHCR 包设为公开，或在服务器使用只具备 `read:packages` 的令牌登录。生产应用部署优先使用提交 SHA 标签，验证后再更新 `latest`。

宝塔站点 `image.yoyo299.site` 的反向代理目标为 `http://127.0.0.1:18080`。申请 HTTPS 证书后强制 HTTPS，并保留 Host、真实客户端地址和 `X-Forwarded-Proto` 请求头；上传大小上限至少覆盖应用允许的最大文件。

## 8. 备份与恢复

- Neon PostgreSQL：启用套餐可用的恢复能力，并每日导出逻辑备份到独立位置；不能把同一项目分支当作唯一备份。
- R2：启用对象版本或业务软删除窗口，定期导出资产清单和哈希。
- 配置根密钥：离线双份保管，不进入普通数据库备份。
- 每月至少一次在独立环境执行恢复演练，而不是只检查备份任务显示成功。

目标：首发 RPO 不超过 24 小时、RTO 不超过 4 小时。规模扩大后再提高到更严格等级。

## 9. 监控告警

- Web：5xx、P95、登录失败率、请求量。
- Worker：队列长度、任务耗时、超时、重试、内存和磁盘。
- 积分：扣费/退款差额、负余额尝试、对账失败。
- R2：上传/下载失败、孤儿对象、存储量和签名失败。
- Sub2API：401、429、5xx、延迟、请求量和估算成本。
- 基础设施：PostgreSQL 连接/容量、Redis 内存、证书到期、备份状态。

严重告警必须通知到站外渠道，不能只显示在已经故障的管理后台。

## 10. 回滚方案

- 应用回滚：镜像按不可变版本标签发布，保留上一个稳定版本。
- 数据库回滚：扩展优先的兼容迁移，先加字段/双写，再切读，最后清理旧结构。
- 配置回滚：后台激活上一配置版本，不回显密钥。
- 流量回滚：Nginx 切回旧只读服务；禁止在新旧系统同时接受写入。
- R2 迁移失败：数据库仍保留源路径和迁移状态，未校验成功前不删除本地文件。

## 11. 上线完成标准

- 域名 HTTPS、Cookie、安全头和反向代理超时配置正确。
- Neon PostgreSQL、Redis、Web、Worker、Scheduler 均健康；Redis 不暴露端口，Web 只绑定回环地址。
- 旧资产抽样下载与哈希验证通过，数量对账无差异。
- 积分并发、任务失败退款和配置回滚演练通过。
- 备份恢复、故障告警和回滚由非开发环境实际演练完成。
